# 准备与播放交接职责修正方案

> 完成日期：2026-10-29。状态：已实施并归档。
> 验证结论：类型检查、16 项既有测试及 9 组定向生命周期检查通过；开发 StrictMode 冷／热交接索引回读均由 1 次降为 0，扫描及媒体进程数不增加，生产热打开复测未见稳定退化。详见[验收报告](../../../../videoCutTool_tmp/20261029-准备与播放交接职责修正/验收报告.md)。
> 源码基准：`91d83a1`。

## 1. 推荐结论与范围

采用**明确打开结果通知 + 工作台统一持有准备引用**的方案。保留准备会话和播放会话，按职责清晰、异步结果正确、运行成本及维护难度选择设计，不以修改文件或行数最少作为目标。

工作台拥有准备会话；播放 Hook 拥有每次播放尝试及其会话。准备引用在当前有效播放请求取得结果，或工作台真实放弃使用时释放。React effect 的清理只结束该次播放尝试，不代表工作台放弃准备。

本方案沿用已完成的[准备与播放数据精简](20261029-素材准备与播放交接精简实施方案.md)，遵循[媒体检查的耗时边界](../../../docs/架构.md#媒体检查的耗时边界)及 [Retention Draft 的常驻规则](../../../docs/adr/0003-retention-draft-and-background-cut-engine.md)。不增加扫描、索引回读、媒体副本、通信往返或等待阶段；性能要求以实施后的定向验收确认。

## 2. 当前问题与方案取舍

[useStreamPlayback](../../../src/renderer/media/useStreamPlayback.ts) 的 `opened` 当前同时出现在打开成功和 `dispose()` 中。开发模式下，StrictMode 会重放首次 effect；第一次清理可能在播放引用取得前释放唯一准备引用，第二次打开因此回读持久索引。问题在于打开结果与资源销毁的含义混在同一个通知中。

| 方向 | 收益与代价 | 结论 |
| --- | --- | --- |
| 只移动 `opened` 调用并补画质对比释放 | 能修复当前时序；但通知名称仍像“打开成功”，失败分支也要调用，后续维护仍需猜测其含义。 | 可用，但不是本次推荐。 |
| 明确打开结果通知，统一工作台持有条件 | 打开通知、播放销毁、准备取消各有明确职责；复用现有状态，不增加协调协议。 | **推荐。** |
| 增加交接协调对象 | 能在对象内拒绝旧尝试结算；但需重复维护 Hook 已有的停止状态，仍要工作台判断真实隐藏。 | 额外状态未带来足够收益。 |
| 抽出完整准备 Hook | 能集中准备、进度和释放；仍需与来源确认、`loadEpoch`、修复提示及草稿初始化协作。 | 适用于整体整理加载流程，本次没有必要扩大到这些职责。 |

## 3. 技术路径

### 3.1 让通知只表达当前打开请求已有结果

将 Hook 的 `opened` 改为 `openSettled`，将 VideoPlayer 的 `onStreamOpened` 改为 `onStreamOpenSettled`，统一语义：

- 当前仍有效的打开请求已经返回或失败，包含流式成功、原生分流和打开失败。
- 已停止的旧尝试不通知，无论其结果迟到成功还是失败。
- 通知不表示首帧就绪，也不表示播放器销毁。

通知只放在包住 `openStream` 等待的局部 `try/finally` 中，并保留本次 effect 捕获的回调：

```ts
try {
  snapshot = api ? await api.openStream(file, id) : null;
} finally {
  if (!stopped) openSettled?.();
}
```

这是控制流示意，不另建 Promise 链或等待任务。外层现有错误处理继续负责错误展示和播放收尾。控制器构造、启动或后续报错不会再次发出打开结果通知。

`dispose()` 仅幂等地销毁本次控制器、清除属于本次实例的引用、关闭本次播放会话。保留现有 `stopped`、`closed`、局部实例及迟到结果检查；不新增尝试编号或交接状态机。

流式成功时，通知发生在 `openStream` 已返回之后、播放器初始化之前：后台播放引用已经取得，随后工作台才释放准备引用。打开失败时也及时释放准备引用。准备释放函数已有幂等保护，继续复用。

### 3.2 用同一条件表达主播放器是否启用

在 [CutterPage](../../../src/renderer/components/CutterPage.tsx) 中统一定义：

```ts
const mainPlayerActive =
  isActive && !isLoading && mainViewportMode === 'player';
```

该值同时用于 `VideoPlayer.isActive` 和**已完成准备引用**的保留条件。工作台的 effect 执行体在 `mainPlayerActive` 为 false 时调用 `preparedStream?.release()`，依赖为 `mainPlayerActive` 和 `preparedStream`；不把该操作放进 effect cleanup。

必须使用捕获当次完成对象的 `preparedStream`，不能读取最新的 `streamPreparation.current` 来代替。两者的现有区别继续保留：

- `streamPreparation.current` 可以指向正在分析的准备会话，包含时间轴异常后继续分析的情况。
- `preparedStream` 只在媒体信息和草稿初始化成功后设置；换片开始时清空。设置完成对象、切回播放视图、结束 loading 和清空 `pendingSelection` 位于同一同步完成段。

因此，准备期间播放器尚未启用，不会触发对正在分析的引用的释放；从画质对比打开新素材时，旧视图状态也不会误关新准备。进入画质对比或离开工作台时，已完成但尚未交接的引用则能够释放。

工作台继续通过 `onStreamOpenSettled={preparedStream?.release}` 接收通知。VideoPlayer 只透传事件，不拥有准备资源，也不理解修复或草稿状态。

### 3.3 加载取消依据加载状态，不依赖引用清理顺序

切 Tab 时，用 `pendingSelection.current` 判断是否仍有未完成的加载，而不再以 `streamPreparation.current` 是否存在决定要不要推进 `loadEpoch`：

- 离开工作台且仍有待完成加载：推进 `loadEpoch`，取消准备；保留返回后的现有重新加载行为。
- 加载已完成：不推进 `loadEpoch`；完成准备引用由主播放器启用条件管理。
- 返回工作台且仍有 `pendingSelection`：沿用现有加载入口。

这样，取消加载不会受另一个 effect 是否已清空引用影响；等待来源确认查询、尚未创建准备会话时，也能过滤过期加载结果。

原生 MP4 在元数据加载完成后启动的后台关键帧提取，此时 `pendingSelection` 已清空，不因切 Tab 被新规则误取消。显式取消、换片和卸载的现有清理继续保留；时间轴异常继续分析及修复流程不迁移。

## 5. 运行成本与边界

| 场景 | 预期行为 |
| --- | --- |
| StrictMode 第一次清理及旧请求迟到 | 只关闭旧播放尝试，不发打开结果通知；准备引用留给有效尝试，交接不回读持久索引。 |
| 当前有效打开成功 | 已取得播放引用后释放准备引用；首帧及定位顺序不变。 |
| 当前有效打开失败 | 释放准备引用并关闭本次播放会话；错误展示及重试沿用现状。 |
| 控制器启动失败或运行时报错 | 准备通知已完成；只处理播放资源，不重复结算打开请求。 |
| 真正隐藏、取消、换片或卸载 | 工作台处理准备资源，Hook 处理播放资源；旧结果不操作新对象。 |
| 未完成准备及异常时间轴分析 | 不因播放器尚未启用而被释放；原有分析与明确取消行为保持。 |
| 原生播放及独立缩略预览 | 保留原路径；不引入额外探测。 |

正常路径的准备／播放请求数量、进度轮询、完整数据生成次数及媒体处理顺序不变。新增判断只使用现有内存状态，不建立新的长期缓存、尝试列表、数组副本或延迟关闭机制。预期收益是消除开发重放中的额外索引回读，不宣称固定毫秒收益。

## 6. 必要验收

按 [README 验证与交付](../../../README.md#验证与交付) 控制验证范围，使用现有一次性 Electron／Playwright 验收入口，不引入组件测试框架或完整 UI 测试工程。

1. 类型检查与既有流式会话、控制器测试通过；测试接口未变时不为此次重命名重写原测试。
2. **实际开发 StrictMode**：延迟首次打开的成功／失败结果，确认旧尝试不释放准备引用；有效播放取得引用后才关闭准备，交接阶段索引回读为零。不能只用生产构建覆盖这一项。
3. **真实离开与加载阶段**：打开尚未完成时进入画质对比、切 Tab；准备／播放均按归属释放，返回可用。补查等待来源确认查询时切 Tab，以及原生 MP4 元数据完成后切 Tab 的后台关键帧结果仍能接收。
4. **错误与既有特殊路径**：当前打开失败后重试、控制器失败后的迟到清理不影响新会话；异常时间轴继续同次分析，明确取消才终止；独立缩略预览保持原行为。
5. 同一代表性 TS、相同工具与索引状态，对比改前／改后的冷、热打开，记录扫描次数、交接索引读取及已有准备／会话取得／首帧计时。正常生产路径不增加媒体工作，未出现可复现变慢；仅在发现差异或失败时复测对应场景。长 FLV 的既有暂缓验收不扩大。

上述为实施时的验收要求；实际覆盖、计时波动、验证脚本修正及未覆盖范围见头部验收报告。报告与一次性验证资产位于仓库同级 `videoCutTool_tmp/20261029-准备与播放交接职责修正/`。
