# 批量压缩导入与保存性能优化实施方案

日期：2026-10-17

状态：已实施并验证，完成日期：2026-10-17。

验证结论：当时记录生产构建、真实 Electron 页面、3 个合计 3.63 GB 的非零起点 FLV 副本、70 项保存、超时取消、未知时长重启、精确检查与存储故障恢复、既有裁剪和预览回归均通过。界面实测三项检查约 0.63 秒、保存约 0.16 秒，保存阶段无媒体工具进程；副本由用户本机 MP4 无损转封装生成，未覆盖另一台电脑的原始 7 GB FLV。现存[界面计时结果](../../../../videoCutTool_tmp/compression-performance-qa/ui-result.json)、[后台结果](../../../../videoCutTool_tmp/compression-performance-qa/backend-result.json)和[恢复结果](../../../../videoCutTool_tmp/compression-performance-qa/recovery-result.json)；独立最终报告未找到，共用 walkthrough 不能替代本任务报告。

## 一、问题与证据

用户反馈：批量选择 3 个 FLV，体量约 7 GB，选入后及保存方案时等待数分钟；尚未区分该体量为单个还是合计，也未采集实际素材的分阶段耗时，不以推测替代实测。

已查证的代码路径：

1. `BatchCompressionPage.checkRow` 在前端逐个检查，`BatchCompressionService.inspect` 在后台也只允许一个检查运行，单个慢素材会挡住后续素材。
2. `MediaTools.probeUncached` 对非零起始时间的 FLV 使用 `ffprobe -show_packets` 遍历全部音视频包，计算精确时长；这一分支没有超时限制。它不做视频转码，但会读取并处理整片数据。
3. `BatchCompressionService.saveOne` 再次调用 `inspect`；检查缓存仅保留 30 秒、最多 64 项。长素材排队或用户调参后容易过期，保存可能重复整片扫描；保存检查还与导入检查共用限流器。
4. `ConfigService.resolveSafeOutputPath` 为选择输出容器再次调用 `probeFile`，通常可命中刚完成的检查缓存，但保存仍依赖媒体探测。
5. 方案逐条保存，每条写入后刷盘并回读验证。尚无实测证据证明这一存储步骤是本次分钟级等待的主要原因。

结论：整片扫描、重复检查和串行等待是已确认的性能风险；用户这批 FLV 与触发条件吻合，实际耗时占比须在实施验收时测量。先前短视频验收覆盖了正确性，没有覆盖此次大体积 FLV 的性能场景。

## 二、已确认的产品行为

- 选择多个文件、统一设置参数、逐项标题、保存为独立方案，维持原流程。
- 选入时只做有资源上限的基础检查，不扫描整段视频；保存时不启动媒体探测。
- 快速检查拿不到准确时长也可保存，显示“时长待确认”；不填假时长，不以 0 秒代表未知。
- 已明确不存在、不可读、不是普通文件或确定没有视频流的素材不能保存；仅仅检查超时、探测信息不足不能直接判为坏文件，允许保存并提示执行时确认。
- 完整媒体检查放到该方案真正进入后台执行时；检查失败只令该项失败，后续项继续，保存成功不等于保证能压缩成功。
- 保存仅保存方案，不自动执行；保留部分成功、失败项重试、同 ID 幂等、编辑冲突及执行中不能覆盖的约束。
- 剩余实现取舍按推荐采用：有限并发、明确待确认状态、复用当前可靠写入流程、按实际执行信息确定输出文件名。
- 本轮只更新方案与术语文档，不修改功能代码、不提交、不推送、不打包。

## 三、技术路径

### 1. 将快速检查与精确探测分开

在 `MediaTools.ts` 增加批量创建专用的快速检查入口，返回路径身份、可读取性、可获取的视频基本信息和检查结论。保留现有精确 `probeFile` 供裁剪、预览及正式执行使用，不通过全局修改其含义来加速批量创建。

快速检查仅读取格式与流摘要，不调用 `-show_packets`、`-show_frames`、关键帧索引、截图、解码或转码。初始采用约 1 MiB 探测预算、1 秒媒体分析预算、3 秒进程超时；这些是资源限制而非“所有磁盘均能在 3 秒内响应”的保证。实施时验证 FFprobe 参数语义及慢进程终止行为，并记录最终参数。

快速入口采用自己的结果类型，不能返回或缓存为精确 `ProbedFile`。容器声明的时长不作为准确时长持久化；首版批量创建统一显示“时长待确认”，执行完成精确探测后再更新记录。分辨率等可得信息正常显示，拿不到则显示“待确认”。

检查结论区分：基础检查通过、待执行确认、明确不可用。仅在证据充分时判定不可用；超时或有限探测未发现视频流不等于已证明没有视频流。工具缺失、权限错误与信息不足分别提示，不用统一的“坏文件”掩盖原因。

后台最多同时运行 2 个快速探测，前端不再以单一 Promise 链串行等待全部文件。限制由后台统一控制，避免大量派生进程；批量加入行时合并状态更新。用户移除、清空时取消对应排队任务和活动探测，忽略迟到回执；切换页面仍保留草稿。取消接口只操作本批量检查请求，不终止后台压缩任务。

文件路径身份沿用规范路径、大小、修改时间等文件属性，仅用于会话内判断素材是否变化，不读取整片内容计算摘要，也不宣称能检测所有内容篡改。保存仍由主进程验证路径授权和文件可访问性，不信任页面自行提交的检查结论。

### 2. 保存仅构造和持久化记录

`BatchCompressionService.saveOne` 移除 `inspect` 和 `resolveSafeOutputPath` 调用。保存只进行参数与标题校验、授权路径检查、轻量文件属性核对、编辑冲突校验、输出目录规则解析和记录写入。

主进程保留当前草稿检查结论；已确定无效且文件未变更的项拒绝保存。素材变更或检查信息不足时，清除旧展示信息并标记待执行确认，不在保存路径自动重跑精确探测。已有方案的独立编辑直接保存参数，仍检查路径和记录冲突，不要求重新扫描素材。

保持逐条独立写入与既有刷盘、回读保护，提供“已保存 X / Y”的进度及逐项错误。先删除重扫描这个已知重开销，不引入批量事务、统一大文件存储或降低保存可靠性；后续计时如显示存储本身显著拖慢，再单独评估。

### 3. 明确未知时长和输出目录的数据表达

将 `PlanRecord` 按 `compressionOnly` 区分普通裁剪记录与整片压缩记录，公共字段保持共享，避免在普通裁剪路径放宽时长不变量。

整片压缩记录允许 `totalDurationMs`、`keptDurationMs` 同时为 `null`；一旦确认，两者必须为相同的正数。普通裁剪记录仍必须具有有效正时长，不允许未知时长进入裁剪规划。精确检查前不格式化未知值、不拿它做进度分母。

整片压缩记录独立保存已解析的绝对 `outputDirectory`，锁定保存时的目录选择；最终 `outputPath` 在尚未生成产物时允许为 `null`，无需为了猜扩展名而提前探测。执行时依据实际音视频流、音频直拷及封面规则选择容器，并使用原有发布防覆盖逻辑生成最终文件名。普通裁剪记录保留其原有输出路径约束。

更新 `CompressionFile`、IPC 类型、记录校验、读取与方案展示；未知时长记录必须能保存、重启读取、编辑、选择执行和失败重试。按项目约定直接更新内部模型，不新增历史数据迁移或旧结构兼容分支，也不自动删除用户数据。旧结构整片压缩记录可能需要重新创建，实施验收使用隔离数据目录并明确记录影响。

### 4. 执行阶段完成精确检查

仅在方案到达后台队列执行位置后运行精确探测；排队提交只进行轻量校验。准备阶段显示“检查视频”，精确时长未知时显示不定进度，不生成虚假百分比或剩余时间。

将精确探测结果作为本次执行上下文传递给后续整片压缩逻辑，避免同一次执行因缓存过期再次扫描同一源文件。精确结果持久化到方案记录后再进入编码；该写入失败遵循现有存储异常暂停和恢复逻辑。重试、新的一次执行或源文件变化不能盲目复用旧结果。

保持非零起点 FLV 的精确时长处理、音轨和封面规则、真实编码进度、容器选择、产物校验及防覆盖发布。此次优化把必要的重工作移到执行阶段，不承诺缩短总压缩耗时；不以容器元数据直接替代原本用于正确性验证的精确结果。

执行失败仍使用现有失败状态和逐项继续策略；准备阶段也必须响应已有停止／退出控制。确保准确时长尚未获得时发生失败，失败记录仍可合法持久化。

## 五、实施顺序

1. 在外部临时目录准备阶段计时与受控媒体样本，记录现有行为；真实大 FLV 仅只读使用，不移动、不覆盖、不输出其媒体内容到日志。
2. 更新记录模型和校验边界，再接入快速探测与不探测的保存路径。
3. 更新执行阶段精确检查、进度与结果回写，保证整片压缩和原裁剪路径各自完整。
4. 更新批量页、方案页及唯一原型，完成异常和取消交互。
5. 构建并进行一次性验证；完成报告双写，验证通过后归档本方案。提交、推送和出包等待用户后续明确要求。

## 六、验收标准

### 性能与调用边界

- 导入和保存期间不出现整片 `-show_packets`／`-show_frames`、关键帧扫描、解码或转码；保存阶段新增 FFprobe 进程数量必须为 0。
- 真实或可控的 3 个大 FLV，分别记录选入到列表出现、基础检查结束、点击保存到全部落盘、执行精确检查的耗时；不要混为一个总耗时。
- 在本机健康磁盘基线下，列表出现目标 1 秒内；3 个快速检查在 2 并发、每项 3 秒进程上限下目标 8 秒内结束或转为待确认；3 条保存目标 2 秒内。以上为需要实测达成的验收目标，不是当前已达成承诺；外置盘、网络盘或操作系统 I/O 阻塞另列结果和限制。
- 调参等待超过 30 秒、同批超过 64 项、重复编辑保存，都不能触发保存时的精确扫描。采用受控工具计数和文件访问证据，不能仅以页面看起来快作为通过依据。
- 若无法取得用户实际大 FLV 路径，使用可控大体积样本并说明覆盖限制，不把短样本通过等同于用户素材已验证。

### 正确性与恢复

- 快速探测超时／时长缺失：显示待确认并可保存；明确非法路径、不可读、确定无视频流：提示错误；混合批次可部分成功。
- 未知时长保存后重启可读，编辑不重新扫描，点击执行后才出现精确检查，成功后显示真实时长与产物路径。
- 输出目录固定于保存时选择；后来修改全局设置不改变该方案目标。实际容器、音轨、封面、命名避让和发布保护保持正确。
- 同 ID 回执丢失重试、部分保存重试、过期编辑、排队中编辑、保存期间素材变化均验证；不能复制生成重复记录或覆盖正在执行的记录。
- 移除／清空时取消检查；迟到回执不复活行；切页仍保留草稿；快速检查和压缩执行互不误取消。
- 准备阶段失败可保存为失败记录且后续继续；精确结果写入失败遵循队列暂停恢复；不因为未知时长出现零分母、NaN 或伪 100%。
- 回归普通无损裁剪、裁剪后压缩、空间裁剪、预览和精确时长逻辑；没有取消其原有校验要求。

### 工具与产出

- 运行生产构建与差异检查；不增加重型测试框架或仓库内 UI/E2E 工程。
- 界面优先使用当前可连接 Electron 的 Playwright 做一次性验证；原生对话框仅在确有需要且 Playwright 无法覆盖时补充其他工具。
- 脚本、日志、截图、样本及报告均放在 `../videoCutTool_tmp/`；成果报告同步镜像到 `../videoCutTool_tmp/walkthrough.md`。
- 验收通过后将本方案移入 `archive/docs/方案/`，在头部写明完成日期、结论和覆盖限制。

## 七、SHA-256 约束与范围

个人 `C:/Users/73839/.codex/AGENTS.md` 明确要求：设计需要使用 SHA-256 时，须取得用户明确授权并在方案中明示；项目根 `AGENTS.md` 没有单独的 SHA-256 条款。本轮的“剩下按推荐”不解释为对 SHA-256 的明确授权。

本优化不新增 SHA-256 使用、不引入视频内容摘要，也不改造项目既有摘要机制。已查到的现存用途是方案恢复记录与缓存标识，未发现本次批量导入／保存对整段视频内容进行 SHA-256 计算；这是现状说明，不是新增摘要设计或对历史授权的追认。
