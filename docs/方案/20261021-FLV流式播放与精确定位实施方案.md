## 1. 用户能够感受到的变化

打开受支持的 FLV 后，直接读取原文件的一小段，处理后交给播放器。播放到哪里，就读取附近的数据；拖到两小时的位置，就从附近的关键帧开始读取。磁盘上不再先生成一份两小时的 MP4 副本。

播放器内部仍可能使用短小的 MP4 数据片段作为浏览器能理解的数据。这些片段在内存中循环使用，不拼成整片磁盘文件。原 FLV、裁剪导出所用素材和已保存方案保持独立。

需要区分两种成本：

1. **整片副本**：本方案针对受支持 FLV 取消它，避免与视频大小相近的重复占用。
2. **定位索引**：记录时间和原文件字节位置，通常远小于视频。没有可靠索引的长片，第一次仍可能需要后台扫描建立索引；不能承诺所有长片第一次打开即可任意位置秒跳。

## 2. 两条路线与推荐

| 路线 | 实际效果 | 主要代价与适用条件 | 结论 |
| --- | --- | --- | --- |
| 保留 Electron 界面，增加 mpegts.js 流式播放 | 常见 FLV 按需读取，保留现有视频元素、遮罩层和时间轴 | 需要可靠字节索引、时间映射、准确寻址；仍受浏览器解码能力约束 | 推荐先做针对性可行性验证，通过后实施 |
| 保留界面，嵌入 mpv/libmpv | 原生媒体内核读取 FLV，格式覆盖更广，提供精确定位和逐帧命令 | Windows 原生桥接、视频表面与网页遮罩合成、DPI、焦点、进程退出和便携打包均需适配 | 流式路线无法通过精度验收时的优先替代路线 |
| 保留界面，嵌入 VLC/libVLC | 使用开源通用媒体引擎播放原文件 | 同样有原生嵌入成本；逆向逐帧等行为仍须针对本项目验证 | 可选原生内核，不能仅凭能播放就认定适合精确裁剪 |
| 换成 CEF、Firefox/Gecko 或其他浏览器内核 | 更换网页运行环境 | 需要重做宿主、IPC 和安全边界；容器和编码支持仍取决于具体构建 | 不推荐作为本次 FLV 问题的解决办法 |

存在其他开源浏览器：Chromium、Firefox，以及可嵌入的 CEF 等。但本项目已使用 Electron；CEF 同样基于 Chromium，更换宿主不能据此推断 FLV 原生兼容。Mozilla 的 GeckoView 官方嵌入入口面向 Android，也不是当前 Windows 项目的直接替换件。这里的投入判断是基于现有代码结构的工程判断，依据见 [Chromium 格式支持](https://www.chromium.org/audio-video/)、[CEF 项目](https://github.com/chromiumembedded/cef)、[GeckoView 文档](https://firefox-source-docs.mozilla.org/mobile/android/geckoview/consumer/geckoview-quick-start.html)。

mpv 和 libVLC 是视频播放内核。它们可以与现有界面配合，不必把整个项目改成另一个浏览器。mpv 文档也说明逆向逐帧依赖精确寻址，部分可变帧率及处理组合存在限制，因此原生内核同样需要实际验收，不能预先保证所有素材逐帧正确。依据见 [mpv 手册](https://mpv.io/manual/stable/)、[libVLC 介绍](https://www.videolan.org/vlc/libvlc.html)。

## 3. 当前调用链中必须处理的缺口

| 当前位置 | 已确认事实 | 本次需要做什么 |
| --- | --- | --- |
| `VideoPlayer.tsx` 的播放错误处理 | 原文件播放失败即尝试 `preparePreview(false)` | FLV 在打开时选择流式路径，流式失败不能自动再生成整片 MP4 |
| `PlaybackPreviewService.ts` | 使用 FFmpeg 输出完整 MP4，再验证并返回文件 | 为受支持 FLV 返回原文件播放会话，停止调用整片换封装；非 FLV 兼容处理独立保留 |
| `KeyframeProber.ts` 的 `FrameIndex` | 关键帧只有媒体时间，没有文件字节位置 | 导出关键帧时间继续使用；新增专门的 FLV 播放字节索引，不把现有索引误当作随机读取索引 |
| `VideoPlayer.stepFrame` | 请求相邻帧时间后马上设置 `currentTime`，没有等实际画面显示 | 每次等目标画面确认后再执行下一次逐帧；超时、取消不得把目标时间当成已显示位置 |
| `CutterPage` 的定位与插入切点 | 定位时先更新界面时间，插入切点读取播放器时间 | 区分请求位置和已确认画面位置，插入切点使用确认值 |
| `media` 协议 | 已有授权检查、文件流和 Range 响应 | 验证流式加载器在实际 Electron 中的请求、取消与背压，并引入会话边界 |
| `probeBasic → probeFile` | 对非零起点 FLV，可能在返回前扫描整片数据包 | 播放准备与精确编辑元数据准备分开，不能只换播放器却继续阻塞在整片探测上 |
| `TimelineThumbnailPreview.tsx` | 小窗是另一个直接读取原文件的视频元素 | 同步接入按需读取能力，不能主播放器可用而切点拖动小窗仍打不开 |

上表是调查基线时的调用链缺口，不是当前全部未修改清单，也不是新路线通过验收的证据；当前实施情况见第 13 节。

## 4. 推荐路线的技术设计

### 4.1 支持范围与失败行为

第一批覆盖常见的 **H.264 视频 + AAC 音频** FLV，以及 H.264 无音轨 FLV；MP3 音轨作为同一阶段的兼容样本验证，通过后才列入支持范围。能力判断同时检查编码参数与实际 MSE 解码能力，不能只根据 `.flv` 后缀判断。

HEVC、增强 FLV、旧 VP6/Sorenson 视频和其他音轨格式不预先承诺支持。mpegts.js 能解析某种编码，不代表当前 Electron 能解码它。遇到未支持格式、严重损坏或无法建立可靠时间轴时明确说明原因，不静默忽略音轨、不显示错误画面，也不自动回退到整片 MP4。

若产品要求上述更广格式全部可用，应选择原生播放内核路线，不能通过增加缓存清理参数解决解码能力问题。

依赖拟选 mpegts.js，flv.js 作为同源方案对照。实施时核对实际发布包并固定版本，不直接跟随 `master`；当前资料中 `master` 的版本号不当作已确认发布版本。MSE 流式换封装能力和配置依据见 [项目说明](https://github.com/xqq/mpegts.js)、[配置说明](https://github.com/xqq/mpegts.js/blob/master/docs/api.md)。

### 4.2 数据读取与播放会话

拟采用的数据路径：

`用户选择的原 FLV → 主进程只读会话 → 按字节范围读取 → 流式解析/换封装 → 内存中的 MSE 缓冲 → 视频画面和声音`

- 主进程在现有可信窗口 IPC 和文件授权检查后创建随机会话 ID；会话记录源文件身份、所属窗口、取消代次及索引引用。
- 首选复用现有 `media` 协议，增加会话 URL；不让页面通过新接口任意打开路径。会话随窗口销毁、换素材和应用退出失效。
- 在实际 Electron 上验证加载器可流式读取自定义协议；Range 为原文件真实偏移，正确返回 206/416、`Content-Range` 和长度，取消必须关闭文件流。
- 如果原生 Fetch 加载器与该协议不配合，采用库已有的 `customLoader` 扩展点，通过受控接口分块读取同一会话；单块拟为 1 MiB，每个播放器至多一个未完成读取，支持取消和背压。接口按窗口和会话校验，不把整片数据通过 IPC 返回。
- 两种传输方式在阶段 A 决定一种，正式代码仅保留选定路径。本方案不增加本地 HTTP 常驻服务，不开放任意路径服务器。
- 文件替换、大小或修改时间变化时使会话与索引失效；源文件身份使用已有规范化路径、文件大小和修改时间信息，不引入内容摘要扫描。
- 保持沙箱、上下文隔离和 CSP。Worker 的入口和加载方式需在阶段 A 核对，不能为依赖运行关闭沙箱或放宽成任意脚本执行。

`customLoader` 的存在依据为库的[配置源码](https://github.com/xqq/mpegts.js/blob/master/src/config.js)与[读取控制源码](https://github.com/xqq/mpegts.js/blob/master/src/io/io-controller.js)；自定义协议是否可直接使用仍需运行验证。

### 4.3 长视频的随机定位索引

**必须解决“从哪个字节开始读”，仅有播放时间不够。** mpegts.js 的寻址逻辑会选择关键帧并跳到对应文件位置，缺少可用索引时不能假定可任意跳转。依据见[寻址控制源码](https://github.com/xqq/mpegts.js/blob/master/src/core/transmuxing-controller.js)和[FLV 索引解析源码](https://github.com/xqq/mpegts.js/blob/master/src/demux/flv-demuxer.js)。

拟新增 `FlvPlaybackIndexService`：

1. 优先读取 FLV 自带的关键帧索引，校验时间与位置数组、单调性、文件范围和实际关键帧 Tag；序列头不当作真实图像关键帧。首次、末尾和实际跳转点均核验，发现错误即弃用该索引。
2. 没有可靠索引时，在后台读取 FLV Tag 结构，跳过不需要的媒体负载，只保留关键帧的原文件偏移、DTS、PTS、必要的编码配置位置及时间基。校验长度、边界、PreviousTagSize 和配置变化；不能只信任 keyframe 标志，更不能把字节位置按视频时长线性估算。
3. 读取分批、有取消信号和并发预算；无可验证边界时报告格式错误，不退化为无限读取或全片解码。首次建索引的耗时单独显示与记录。
4. 索引未完成时允许顺序播放和已知范围定位；未索引的远处显示“正在建立定位索引”，不从文件开头偷偷播放到目标位置。索引完成后支持全范围随机定位。
5. 对同一源文件共享后台索引任务；一个播放器关闭不误取消另一个消费者。切换素材后，旧结果不得写入新会话。
6. 索引作为可再生 JSON 资产接入现有缓存维护，写入前登记，发布原子完成，使用期间持有引用；配置、已保存方案和验收记录不参与回收。旧整片缓存和未知历史目录不自动认领或迁移。

**依赖适配成本必须算入方案。** 已查阅的公开 API 没有给出完整的外部关键帧索引注入接口，不能假定传一个普通配置即可实现。阶段 A 按需要小范围受控源码补丁估算：提供外部索引输入、重置时保留索引以及统一时间基的可观察信息；固定上游源码与最小补丁，验证可重复生成依赖产物。禁止运行时随意改库私有字段，禁止只修改本机 `node_modules`。

阶段 A 必须给出具体依赖版本、补丁差异和构建办法。若改动扩展到大范围重写解复用或换封装，停止这一路线，重新选择原生播放内核，不把维护一个大型播放器分支隐藏在“小改动”中。

### 4.4 定位完成与逐帧操作

定位分为两步：先找到目标之前的可解码关键帧，再解码到目标显示帧。底层从关键帧开始读取，不代表界面只允许停在关键帧。

- 普通拖动合并高频请求，只保留最新目标；拖动过程中限频预览，松开后必须完成最终精确定位。
- 每次定位有独立代次。旧读取、旧解码和旧回调不能覆盖最新目标；回退到文件开头、接近末尾、跨 GOP 和快速反向拖动均使用同一规则。
- 区分 `requestedTime`、`presentedTime` 和定位状态。请求位置可以作为待定位标记展示，切点和逐帧基准使用已确认的源视频展示时间。
- 逐帧继续使用源文件真实相邻展示帧的 PTS，复用并改进 `adjacentFrame` 附近窗口读取；不能以平均 FPS 的倒数代替可变帧率的真实间隔。
- `adjacentFrame` 补充取消、请求代次和限流；窗口中未找到目标相邻帧时，从可靠的前置关键帧扩展读取，不能返回 0 或原时间并当作成功。
- 一次逐帧等待目标帧实际呈现后才处理下一次。结合 `seeked`、`requestVideoFrameCallback` 的 `mediaTime` 及目标附近帧 PTS 确认，比较真实帧号/像素证据；仅有 Promise 返回或游标数值变化不足以算成功。
- 不沿用未经校验的固定 `+0.001 ms` 修补。目标落点按相邻帧展示区间选择，并确认呈现帧属于目标；不能通过播放几帧再暂停的方式冒充准确定位。
- 文件切换、超时、取消或解码错误时终止逐帧队列，保留最后确认位置。定位中禁止按未确认位置插入切点；成功后恢复原有暂停/播放和倍速意图。

库的 `accurateSeek` 是拟启用的能力选项，不是逐帧正确性的验收证明。[帧呈现回调文档](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)说明它能返回呈现帧的媒体时间，但它本身不是逐帧控制接口。

### 4.5 源视频时间与音画同步

- 所有编辑、切点和导出继续使用源视频相对时间，沿用现有 `MediaTime` 和有理数运算；不把播放器归零后的时间直接写入方案。
- 记录源时间原点和流式换封装时间基，建立可逆映射：`播放器展示时间 = 源相对展示时间 + 会话偏移`。偏移从真实时间戳和首个呈现帧校准，不能只用文件名、元数据 duration 或固定常数推断。
- 音视频使用同一个会话映射，保留其原有起始差；不能分别把音频、视频首帧都减为 0。保留 PTS 与 DTS 的区别，按展示顺序验证带 B 帧素材。
- 非零起点、首包负偏移、可变帧率和末尾时间必须覆盖。时间戳中途重置或跳变不能靠一个固定偏移掩盖；第一批遇到无法可靠映射的文件应明确拒绝精确编辑，不自行承诺修复全部异常直播录像。
- 媒体库的音频补静音与时间戳修正行为需单独核对；先保留源时间关系，再决定参数。不能凭默认开关认定同步正常，也不手工重写时间戳来追求看似连续。
- 关闭直播追赶、追赶式变速和直播窗口配置，文件播放明确设为点播；倍速继续由用户设置。
- 同步验收既检查原始时间戳映射，也检查真实播放中声音和画面标记的对应，不能只比较同一播放器报告的两个时钟。

### 4.6 有界缓冲与资源回收

第一轮拟从前向约 30 秒、后向约 10 秒的内存缓冲目标开始，并结合字节量、播放器反馈和 GOP 大小调整；这是预读窗口，不是视频总长或文件大小限制。解码必须需要完整 GOP 时允许临时扩展，完成后回落；不因单个长 GOP 直接截断数据。

- 读取、JS 队列和 MSE 缓冲均有背压；播放暂停且缓冲足够时停止预读，避免暂停一晚读完整片。
- 启用并验证 MSE 旧数据回收；内存压力时先减少闲置缓冲，再定位重建，不能退回生成整片磁盘副本。
- 每个视图至多一个主播放实例；切点小窗按可见性创建独立静音实例，读取预算受控，可复用只读索引，不能占用或拖动主播放器。
- 隐藏页面暂停读取；卸载、换素材、取消和退出时停止加载、释放 SourceBuffer/对象 URL/Worker/文件句柄和索引引用。异常退出不留下整片派生文件。
- “不生成整片 MP4”不等于进程零内存、系统零文件缓存；验收分别统计新增媒体文件、索引字节、JS/进程内存和读取量。

### 4.7 播放启动与编辑元数据解耦

当前名为 `probeBasic` 的路径仍可能执行精确时长的整片数据包扫描。新增轻量播放会话描述，先取得编码、画面尺寸、初始化数据及时间映射所需信息；播放不等待完整关键帧分析或整片时长确认。

`CutterPage` 先持有选中的源文件和播放会话，精确 `MediaMetadata` 与编辑草稿随后建立。时长未知或尚待确认时，显示准备状态，不能用猜测的时长创建或覆盖已保存方案；需要精确边界的保存和执行继续使用已确认数据。批量压缩选入、调参和保存仍不得增加整片扫描。

尾部快速读取只能用于有可靠 Tag 边界的情况；不能把任意尾部字节中的模式匹配当成准确时长。无法快速确认时后台校验并展示状态，不承诺所有素材首次完整时间轴都能瞬间可用。

## 6. 实施顺序与停止条件

### 阶段 A：先证明关键能力

所有一次性脚本、样本、日志和截图放仓库同级 `../videoCutTool_tmp/`，不建立新的测试工程。

1. 固定候选库版本，在本项目实际 Electron、沙箱和协议下播放本地 H.264/AAC FLV；记录真实 Range、取消和读取量。
2. 用有索引、无索引及坏索引样本验证随机定位；确定外部字节索引的受控接入补丁和构建办法，确认首关键帧不会被错误跳过。
3. 用非零起点、B 帧、可变帧率样本验证源时间映射及正反逐帧，实际核对呈现帧号和声音标记。
4. 在长视频后半段随机定位，确认读取从邻近关键帧开始，没有从头扫到目标、没有整片写盘、没有无界预读。

若外部索引接入不可维护、精确呈现不可靠、存在无法消除的同步漂移或实际 Electron 无法稳定运行，停止正式接入并记录失败证据。此时转为评估 libmpv，而不是降低逐帧标准或悄悄恢复整片缓存。

### 阶段 B：接入正式播放与定位

阶段 A 通过后实现会话、索引和播放控制器，接入页面、时间轴及小窗。按理想设计替换 FLV 的旧整片路径；保留非 FLV 的合法处理逻辑，不引入旧接口迁移层。

### 阶段 C：资源和错误收尾

覆盖快速换片、快速拖动、取消索引、取消读取、隐藏/恢复、MSE 满缓冲、源文件变化、窗口关闭和程序退出。原文件、配置、已保存方案和验收证据逐项保护。

### 阶段 D：定向验收与交付

先类型检查和受影响的时间映射/索引纯逻辑测试，再做实际 Electron 和媒体验证。通过即停止扩展检查。是否打包、提交或发布按用户后续明确指令执行，不能用开发态通过代替包内验证。

### 7.1 样本与操作

| 场景 | 要证明的结果 |
| --- | --- |
| 两小时以上、真实高码率长 FLV | 没有与整片大小近似的 MP4 派生文件，首次/二次索引成本分别记录 |
| 有、无、错误关键帧元数据 | 正确使用或重建索引；未知范围明确等待，不能伪报跳转完成 |
| 首部、25%、50%、90%、末尾和往返定位 | 冷/热缓冲均停在正确展示区间，最后一次请求获胜，读取量与目标邻域相关 |
| 长 GOP、B 帧、VFR | 连续前后各 20 次逐帧，跨 GOP 后帧号和源 PTS 正确，无跳帧、重复确认或游标先行 |
| 非零起点、音视频首包偏移 | 源时间映射可逆，切点时间和独立 FFmpeg 读取到的原帧一致 |
| 带同步闪光/短音标记样本 | 开始、随机定位后和长时间播放后音画关系保持；同时核对源本身的音画差 |
| 0.5×、1×、2×、暂停/恢复及区间试听 | 倍速和声音正常，暂停逐帧不漏音，试听端点使用确认时间 |
| 裁剪框、遮罩、小窗和分段切换 | 显示区域、SAR/旋转和确认时间保持，切点小窗不拖动主画面 |
| 快速切换 10 个素材、拖动 30 次 | 无旧画面覆盖新素材、无未处理拒绝，文件句柄/读取队列/Worker 可回落 |
| 不支持的编码、损坏文件和参数变化 | 明确失败或停用相应精确操作，不自动产生整片缓存，不丢弃原音轨后伪报成功 |
| 选入、保存方案和导出回归 | 流式播放索引不会给轻量批量保存增加整片探测；从原文件导出的切点及画面正确 |
| 未授权窗口/会话、越界 Range、源文件替换 | 拒绝请求且不读取其他文件，取消与退出释放资源 |

### 7.2 度量方式和拟定目标

- 记录参考机器、磁盘、Electron/库版本、视频编码/码率/大小/时长/GOP，以及有无索引。使用 1080p H.264/AAC、本地 SSD 的可重复样本作为基准；4K、长 GOP 和慢盘单独列结果。
- 基准拟定目标：已具备可靠索引时首画面不超过 3 秒；30 次跨位置定位的热缓冲外 P95 不超过 2 秒；附近窗口已就绪时逐帧 P95 不超过 500 毫秒。首次无索引的扫描耗时另列，不能混入热缓存数据或承诺与文件时长无关。
- 精度优先于速度：逐帧目标必须与源帧号/PTS 一致；普通定位必须显示包含目标时刻的帧。不能用几十毫秒容差把错误的相邻帧也算正确。
- 同步样本拟以相对原片的额外音画偏移不超过 80 毫秒、连续播放 30 分钟无持续增长为初始验收目标；用可观察的画面标记与实际音频输出采集测量，并报告采集误差。仅查看 `currentTime` 或音视频都在播放不足以验收。
- 2026-10-24 用户确认的归因口径：正常素材检查播放器新增的偏移；异常原片单独检查修复效果，不以原片异常豁免修复副本的验收。采集缺口不计通过；孤立超标原样保留并复核，既不直接归为播放器故障，也不默认归为采集误差。先核对采集完整性和测量误差，再根据证据决定是否修复播放器。
- 记录源文件读取字节数、索引文件大小、进程与 JS 内存、MSE 缓冲区间及实例数。暂停后读取应停止增长，重复操作后资源应回落；不能把浏览器内存统计不完整解释为没有泄漏。
- 上述数值是待验证的工程目标。阶段 A 先跑基准；达不到时如实记录原因和支持边界，不在交付时偷偷放宽或把低码率小样本替代真实高码率长片。
