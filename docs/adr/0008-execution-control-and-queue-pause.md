# 0008. 任务执行停止与队列级暂停控制架构决策

> 状态：有效。2026-11-14 明确停止与暂停控制语义、规避 Windows 进程挂起孤儿风险与状态回收规则。

## Context

在单片剪辑导出与批量压缩任务中，用户需要对后台运行的任务进行“停止”与“暂停/恢复”控制。
但 FFmpeg 在 Windows 平台下未提供命令行或通信协议级别的“暂停/恢复”机制。若通过 Windows 系统 API（如挂起进程主线程或 `NtSuspendProcess`）实现强制挂起，一旦 Electron 主进程或 Node.js 运行时发生崩溃或强退，被挂起的底层 FFmpeg 子进程极易脱离管理成为“孤儿进程”，持续霸占系统内存和视频文件句柄，甚至必须重启电脑才能解除文件占用。
此外，单个视频导出或长视频转码通常耗时较长，若误触停止会导致前期转码进度全部丢失；而尚未执行的排队任务则无进度损失。

## Decision

- **任务中断停止（Task Abort）**：
  - 单任务停止通过现有的 `AbortSignal` / `AbortController` 中断底层 FFmpeg 进程，由 `CacheMaintenanceService` 物理回收该次执行名下的临时切片目录与未完成产物，解除文件锁定。
  - 停止后方案的持久化状态**直接重置为 `ready`**（不扩展取消专用持久化状态，不产生失败报错信息），便于用户直接重新调整或重新发起。排队中（`queued`）任务移出队列亦直接重置为 `ready`。
  - 防误触策略：针对执行较慢、进度宝贵的正在处理（`processing`）任务及全局【全部停止】操作，强制提供应用内二次确认提示；排队中未开始的任务移出队列则不弹窗，操作保持敏捷。
- **队列调度级暂停（Queue Pause）**：
  - **杜绝系统级进程挂起**：为消除孤儿进程与句柄死锁风险，不采用任何底层的进程挂起黑魔法。
  - 暂停控制作用于 `MediaCuttingEngine` 的队列派发层：处于暂停状态时，当前正在处理的单任务继续安全完成，后续排队任务保持 `queued` 状态暂不派发；用户若连当前任务也不想继续，可显式点击单任务【停止】。
  - 队列暂停期间新提交的方案静默进入排队队列等待，严格尊重用户的暂停意图，不自动开跑；恢复队列派发后按原顺序依次执行。

## Consequences

- 彻底消除了底层孤儿进程、僵尸进程与文件长期占用的不可逆系统风险。
- 单任务想要立刻腾出全部硬件资源时，通过显式“停止”并回收临时文件来实现；队列级暂停则满足了多任务批量转码时让出计算机算力的需求。
- 方案持久化状态保持精简，避免了状态机复杂化；防误触确认策略在保护长时间转码成果与轻量排队调整之间取得了平衡。
