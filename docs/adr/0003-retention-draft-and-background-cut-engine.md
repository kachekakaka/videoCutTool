# 0003. RetentionDraft 领域深模块与后台异步剪辑引擎架构决策

## Context
在前期架构演进与审查中，发现了两项直接影响数据一致性、前后台协作与交互流畅度的重大架构摩擦点：
1. **草稿状态散落与切点删除导致的隐蔽决策漂移**：
   在前端 CutterPage 中，时间轴状态被割裂为独立的 cuts: number[] 和 decisions: Record<string, RetentionDecision>。当用户在时间轴上删除某个中间切点时，分段索引重新从 0 编号，导致用户原本标记的保留/丢弃决策产生索引错位，误将正片标记为丢弃。同时，切点转分段逻辑在前端与主进程各有一套重复实现。
2. **剪辑执行双轨制与前台阻塞等待**：
   此前工作台“立即执行剪辑”采用前台同步等待模式，前端手动计算路径、调用 cut:execute 阻塞等待 FFmpeg 流复制切片与合并，完成后再通过反向 IPC 调用 plan:save 将方案状态由前端落盘；而在“方案管理中心”又由主进程 PlanManager 独立处理。操作员在等待剪辑时无法无缝进行下一个视频的处理。

## Decision
经过多轮访谈（Grilling）与领域建模，确立以下核心架构设计：

1. **构建核心领域深模块 RetentionDraft**：
   - 将“剪辑草稿”提升为自包含、高内聚的深模块（src/shared/RetentionDraft.ts）；
   - **不变量安全防护**：切点间距低于 200ms 或距视频首尾过近时自动拒绝；分段保留/丢弃状态绑定稳定段落对象，消除索引漂移；
   - **删除合并的安全保全规则**：当删除切点导致相邻分段 A 和 B 融合为新分段时，严格贯彻“绝不多删一帧正片”原则，只要 A 或 B 中存在任一 keep，新融合段落即判定为 keep；
   - **内存常驻生命周期**：草稿在工作区会话内存中常驻，跨 Tabs 切换视图保持完整状态，仅在显式打开新视频或载入外部方案时重置；
   - 提供唯一的 .toPlan() 转换方法输出不可变的 MediaRetentionPlan，收敛前端与主进程两套推导逻辑。

2. **建立统一的后台异步剪辑引擎（MediaCuttingEngine）**：
   - 彻底废除前端跨进程编排与状态反向保存；
   - 将剪辑执行统一收口至主进程后台引擎，建立**单任务串行队列（FIFO Queue）**，保证同一时刻仅运行 1 个 FFmpeg 实例，避免磁盘 I/O 争抢和 CPU 抢占，确保前台剪辑与视频播放如丝般顺滑；
   - **方案状态机唯一真源**：方案生命周期由主进程引擎管理，状态定义以 [Execution Status](../../CONTEXT.md) 为准。入队、开始和完成均等待持久化成功；重复提交复用已接受任务，界面按单条记录变更更新；
   - **前端移交交互流线**：工作台点击“立即执行”时，草稿自动保存为方案并直接移交给后台执行队列，工作台底部弹出轻量 Toast 提示，画面保持不变，操作员可立即继续操作或打开新视频。

3. **全局通知与偏好可配置**：
   - 当后台静默剪辑完成时，向前端广播完成事件，触发全局 Toast 浮动提示，并支持“一键在文件管理器中定位产物”；
   - 在“系统设置（Settings）”中增加【导出完成时弹出全局通知】开关偏好（notifyOnExportComplete，默认开启），满足用户个性化通知需求。

## Consequences

### 2026-09-12 后续修订

方案主记录更新前，先在 Data Directory 的 `plans_recovery/` 保留并校验上一份完整快照；主文件刷盘并回读成功后才更新内存索引。启动和手动刷新可恢复损坏记录，并显示恢复问题；中断任务不会自动重新导出。删除标记先持久化，禁止已删除 ID 的状态回写。完成状态保存失败时保留待保存结果并暂停队列，恢复写入后继续保存，避免重复导出。启动与手动刷新使用受限并发异步读取，其余变更维护内存索引。
- **彻底根除决策漂移 Bug**：通过 RetentionDraft 内部不变量，无论用户如何高频增删切点、微调边界，正片保全决策永不丢失；
- **生产力质感大幅提升**：前台工作台与后台执行彻底解耦，达成“前台秒级打标连贯作业、后台静默稳健队列生产”的专业桌面体验；
- **架构 Locality 与 Leverage 跃升**：消除了 4 个细粒度的 IPC 穿透与前端反向数据保存，状态机逻辑 100% 闭环于主进程引擎，测试表面大幅精简。
